A-01 · Qualquer pessoa logada consegue encerrar o ciclo de metas da empresa inteira

Hoje, mesmo um Vendedor — o nível mais baixo da hierarquia — consegue fechar sozinho o ciclo mensal de metas, e até fechar incompleto, sem nenhuma meta ter chegado no fim da cascata. Essa ação deveria ser só do Administrador; foi um esquecimento de configuração, não uma decisão de projeto.

A correção é uma linha de código (close entra na lista de ações restritas ao Administrador) e não tira acesso de ninguém que já devia ter essa permissão — a única tela que usa esse botão já é uma tela de administrador.

Prioridade alta

2 itens restantes (o 3º, A-01, está acima)
A-02Alta

O sistema aceita senha fraca, tipo "1"

As regras de senha forte já existem configuradas (tamanho mínimo, não pode ser só número, não pode ser uma senha comum) — só que nos 3 lugares onde uma senha é criada ou trocada (cadastro de usuário, troca de senha, redefinição por e-mail), essas regras nunca são de fato aplicadas. Testando: hoje dá pra definir a senha "1" sem nenhum aviso.

Muda um pouco, do jeito esperado

Depois de corrigido, criar ou trocar senha vai exigir uma senha de verdade. Não é uma trava nova — é a trava que já devia existir passando a funcionar.

apps/accountsEsforço: baixo
A-03Alta

Não existe limite de tentativas de login

O sistema aceita quantas tentativas de senha alguém quiser tentar, sem pausa nem bloqueio — o que deixa em aberto um ataque de "força bruta" (ir tentando senha atrás de senha até acertar). Isso pesa mais porque o app hoje também é acessado de fora da rede da empresa, por um túnel.

Não muda nada pra você

Ninguém que usa o sistema normalmente percebe diferença. Só passa a demorar (ou travar por um tempo) quem errar a senha várias vezes seguidas rápido demais.

M-01Média

A conexão não está 100% travada contra espionagem

O cookie que mantém você logado não está marcado pra viajar só por conexão criptografada, e faltam alguns reforços de segurança de transporte. Isso importa porque o app hoje é acessado de fora pela internet, via um túnel.

Precisa de uma decisão sua

Antes de ligar essa trava, precisamos decidir: o app só é acessado pelo túnel (sempre criptografado), ou também direto pela rede local? Ligar sem essa definição pode fazer ninguém mais conseguir logar.

config/settings.pyEsforço: baixo
M-02Média

O app roda com o "servidor de teste", não o de produção

Backend e frontend ainda rodam no modo usado durante o desenvolvimento — o próprio Django avisa que esse modo não é feito pra ficar exposto fora do computador de quem programa. Se der um erro, a tela pode mostrar pedaços do código-fonte e dados internos pra quem estiver de fora.

Precisa de uma decisão sua

Essa é a mudança mais estrutural do relatório inteiro: trocar pro servidor de produção é um projeto próprio (novos arquivos de configuração, novo processo de build), não um ajuste rápido. Vale planejar em separado.

docker-compose.ymlEsforço: médio/alto
M-03Média

Uma tela mostra pendências de ramos que não deveriam aparecer

Ao checar se um ciclo pode ser fechado, o sistema devolve as pendências de todos os ramos da hierarquia, não só do que a pessoa logada tem acesso. Só que essa checagem hoje só é usada pela tela de fechamento de ciclo, que já é restrita ao Administrador.

Não muda nada pra você

Corrigir fecha uma brecha teórica (alguém chamando a API por fora do app), sem afetar quem já usa a tela normalmente.

M-04Média

A porta do banco de dados está aberta, com senha padrão

Dá pra conectar direto no banco de dados pela rede, e se ninguém tiver configurado uma senha própria, vale a senha padrão que está escrita no próprio arquivo de configuração do projeto.

Muda um pouco, do jeito esperado

Fechar essa porta é o certo, mas tira a conveniência de conectar direto no banco por fora (ex: DBeaver) pra olhar dados manualmente — ainda dá pra acessar por dentro do container Docker.

Nomes exportados podem virar "fórmula" no Excel

Se um nome vindo do sistema de vendas começar com sinais como =, +, - ou @, o Excel pode interpretar isso como fórmula ao abrir o arquivo exportado. Risco baixo, porque esses nomes vêm de um sistema interno da própria empresa.

B-04Baixa

Chave secreta do sistema tem um valor padrão de reserva

Se a variável de configuração da chave secreta do Django não for definida, o sistema usa um valor padrão conhecido publicamente, em vez de recusar iniciar.

Não muda nada pra você

config/settings.pyEsforço: trivial

O que já está certo — não mexer

Esses pontos foram checados especificamente e passaram. Registrados aqui pra reconhecer o que já foi bem feito, e pra ninguém "consertar" o que não está quebrado.

✓Nenhum jeito de injetar comando no banco de dados (SQL injection)
✓Cada pessoa só acessa as metas do próprio ramo, mesmo tentando forçar por fora
✓O frontend não deixa código estranho ser executado dentro da tela (XSS)
✓Sessão de login guardada em cookie, não em um lugar que outro script leria
✓Nenhuma execução de código externo perigosa no backend

Ordem recomendada

Do mais urgente e mais barato de corrigir, até o que exige mais planejamento.

  1. Fechar a brecha do encerramento de ciclo (A-01). Uma linha de código, hoje mesmo.
  2. Ativar as regras de senha e o limite de tentativas de login (A-02, A-03). Baixo esforço, sem quebrar fluxo de ninguém que já usa senha de verdade.
  3. Decidir a forma de acesso ao app e então travar cookies/HTTPS e fechar a porta do banco (M-01, M-04). Precisa da definição: só túnel, ou também rede local.
  4. Planejar a troca pro servidor de produção (M-02). Tratar como projeto à parte, não como ajuste pontual.
  5. Fechar o vazamento entre ramos, neutralizar o CSV e reduzir o prazo do link de senha (M-03, B-01, B-02). Baixo esforço, sem impacto de uso.
  6. Travar versões de dependências e exigir a chave secreta (B-03, B-04). Mexe só no processo de build.
